# AchieveNest Evidence Upload Security

## Status

Security-critical implementation for Student Portfolio and Personnel accomplishment evidence.

**Database target validated:** `AchieveNest-Test` only.  
**Production:** not modified.  
**Merge gate:** repository migration history must be reconciled before merging the migration file into `main`.

## Security model

Sensitive evidence is backend-mediated. The browser does not directly create permanent Supabase Storage objects and does not provide trusted MIME type, byte size, checksum, malware status, or permanent object path.

Upload flow:

1. Authenticated user submits a multipart `file` to the CodeIgniter API.
2. Backend verifies record ownership and editable workflow state.
3. Backend reads the temporary uploaded bytes.
4. File size is limited to 20 MB.
5. MIME type is detected server-side with `finfo`.
6. Actual magic bytes must match PDF/JPEG/PNG/WebP.
7. PDFs containing active/embedded content markers such as JavaScript, OpenAction, Launch, EmbeddedFile, RichMedia, SubmitForm, ImportData, or XFA are rejected.
8. SHA-256 is derived from the actual bytes.
9. Malware scan is executed using `clamdscan` or `clamscan`.
10. Malware scanning is fail-closed by default.
11. Backend generates the permanent Storage object path.
12. Backend uploads the clean object using the server-only Supabase service role.
13. Only after upload succeeds is evidence metadata persisted with `security_status=clean`.
14. A file-security audit event is written.
15. If metadata persistence fails, the uploaded object is deleted as compensation.
16. Downloads require application authorization and return a signed URL valid for at most 120 seconds.

## Allowed types

- `application/pdf`
- `image/jpeg`
- `image/png`
- `image/webp`

Supabase buckets remain private.

## Malware scanner configuration

Install ClamAV on the backend host and configure:

```ini
EVIDENCE_MALWARE_SCAN_REQUIRED = true
EVIDENCE_MALWARE_SCANNER_PATH = '/usr/bin/clamdscan'
```

`clamdscan` is preferred when the ClamAV daemon is available. `clamscan` is also supported.

If scanning is required and the scanner is missing, unavailable, times out, or returns an error, the upload is rejected. Do **not** disable the scan requirement in production.

## Storage access

Direct authenticated-user Storage policies for `student-evidence` and `personnel-evidence` are removed in AchieveNest-Test. Evidence Storage access is server-mediated with the service role.

Object paths are generated by the backend:

```text
student-evidence/{student_uuid}/{portfolio_record_uuid}/{evidence_uuid}.{ext}
personnel-evidence/{personnel_uuid}/{accomplishment_uuid}/{evidence_uuid}.{ext}
```

Clients cannot select an arbitrary permanent path.

## Database enforcement

Evidence rows include:

- `security_status`
- `detected_mime_type`
- `sha256`
- `malware_scanner`
- `security_validated_at`

Database triggers reject evidence registration unless:

- `security_status = clean`
- detected MIME is present
- SHA-256 is present
- malware scanner is recorded
- validation timestamp is present
- legacy `checksum` equals `sha256`
- stored MIME equals server-detected MIME

Authenticated clients do not have direct INSERT/UPDATE/DELETE privileges on evidence metadata tables.

## Authorization

Student evidence download is allowed only for:

- the Student who owns the record;
- an active Program Coordinator assigned to the Student's active Academic Program;
- OSAD Admin.

Personnel evidence download is allowed only for:

- the Personnel owner;
- HR Admin;
- the active Dean of the Personnel's active College.

UI visibility is not treated as authorization. Every download request is checked server-side.

## Camera scanning

This security implementation accepts images produced by a phone/document camera because JPEG, PNG, and WebP are allowed. A dedicated multi-page camera-scanner UI and OCR are separate UX/features and are not claimed as implemented by this security change.

A later scanner UI must submit its resulting image/PDF through the same secure multipart endpoint; it must not receive a security bypass.

## Tests

`EvidenceFileSecurityServiceTest` covers:

- clean PDF inspection and SHA-256 derivation;
- active JavaScript/OpenAction PDF rejection;
- disguised fake PDF rejection;
- oversized evidence rejection;
- fail-closed behavior when malware scanning is required but unavailable.

## Remaining platform hardening outside this upload implementation

Supabase Security Advisor currently still reports pre-existing WARNs for exposed `SECURITY DEFINER` helper functions and disabled Auth leaked-password protection. These are separate project-wide hardening tasks and must be completed before production.
