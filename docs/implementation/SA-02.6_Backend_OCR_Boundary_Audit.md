# SA-02.6 — Backend OCR Boundary Audit

## 1. Document Purpose
This audit verifies the boundary protections enforced across backend API controllers, persistence models, and services in AchieveNest to guarantee that OCR extraction suggestions can never mutate protected workflow fields or bypass evaluator verification.

---

## 2. Backend Security & Workflow Boundary Rules

```
┌────────────────────────────────────────────────────────────────┐
│ Student Client Request (Payload includes OCR suggestions)       │
└───────────────────────────────┬────────────────────────────────┘
                                │
                                ▼
┌────────────────────────────────────────────────────────────────┐
│ StudentAchievementController (API Entry Point)                 │
│ 1. Filters input payload through strict field whitelist        │
│ 2. Strips FORBIDDEN_METADATA_KEYS                              │
│    (score, points, calculated_points, verified_by, etc.)       │
│ 3. Enforces initial status = 'draft' or 'submitted'            │
│ 4. Assigns student_profile_id strictly from Auth Context       │
└───────────────────────────────┬────────────────────────────────┘
                                │
                                ▼
┌────────────────────────────────────────────────────────────────┐
│ Database Persistence Layer                                     │
│ - status = 'draft' / 'submitted' (NEVER 'verified')            │
│ - verified_by = NULL                                           │
│ - score / points = NULL / 0.00                                 │
└────────────────────────────────────────────────────────────────┘
```

---

## 3. Audited Protected Fields and Enforcement Matrix

| Field Name | Target Table | OCR Injection Risk | Backend Enforcement Mechanism | Protection Status |
|---|---|---|---|---|
| `status` | `student_achievements` | Client attempts to send `status: "verified"` based on high OCR confidence. | Hardcoded initial state logic in `StudentAchievementController`. Status only transitions to `submitted` or `draft`. | **PROTECTED** |
| `verified_by` | `student_achievements` | Client attempts to inject fake evaluator ID. | Controller rejects or ignores input; populated exclusively during OSAD evaluator verification action. | **PROTECTED** |
| `verified_at` | `student_achievements` | Client attempts to supply timestamp. | Database timestamp generated exclusively upon evaluator approval. | **PROTECTED** |
| `score` / `points` | `student_achievements` / `portfolio_scores` | Client attempts to claim award points. | Stripped by `FORBIDDEN_METADATA_KEYS` guard; points calculated strictly by backend scoring engine (`AwardRuleEvaluatorService`). | **PROTECTED** |
| `student_profile_id` | `student_achievements` | Client attempts to assign achievement to another user. | Overridden strictly from authenticated session token (`$auth->user_id`). | **PROTECTED** |
| `id` (Primary Key) | `student_achievements` | Client attempts to overwrite existing records. | Auto-incremented primary key generated by database engine. | **PROTECTED** |

## 4. Hash Consistency & Provenance Isolation

As implemented in `PersonnelEvidenceOcrIntegrationService.php` and `LocalEvidenceStorageService.php`:
1. **SHA-256 Hash Verification**: When OCR runs against stored evidence, the file binary SHA-256 hash is computed and verified against the stored hash in the database.
2. **Decoupled Failure**: An OCR extraction failure or malformed PDF raises an internal error or falls back to manual entry, but **never** deletes or invalidates the uploaded evidence file.
3. **Audit Trail**: Any OCR execution metadata (e.g. `ocr_status`, `ocr_source_evidence_id`) is stored as informational processing trace and never as verification proof.

---

## 5. Acceptance Verification

All backend boundaries strictly comply with SA-02.6 requirements:
- OCR suggestions cannot modify workflow state.
- Zero verified records can be generated without human evaluator review.
- System integrity remains intact against client-side tampering.
